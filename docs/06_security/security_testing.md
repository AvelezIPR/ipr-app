## 0. Reglas del plan

| Regla | Detalle |
|---|---|
| Entorno | Pruebas dinámicas **solo en staging** (frontend + BFF + WordPress/WooCommerce + Wompi sandbox) o en local. **Ninguna prueba ni escáner contra producción** sin autorización expresa y escrita (D-16). La existencia de staging es DESCONOCIDA (C2): si no existe, las pruebas dinámicas quedan bloqueadas (NLS-08). |
| Datos | Solo **sintéticos**: cuentas `qa.cliente.a@ejemplo.test`, `qa.cliente.b@ejemplo.test`, `qa.admin.rol@ejemplo.test` (rol con `edit_posts`, creado en staging), contraseñas generadas por la prueba y guardadas en el gestor de secretos de QA; productos de prueba (publicado, borrador, privado, oculto, con contraseña, sin precio, agotado); **valores canario** para detectar fugas: correo `canario.pii@ejemplo.test`, cédula `CANARIO-9990001`, teléfono `3000000999`, dirección `Calle Canario 99`, contraseña `Canario-Pass-0001`. Nunca datos reales de clientes ni de empleados. |
| Tarjetas | Solo las tarjetas y medios de prueba publicados por Wompi para su *sandbox*. |
| Dispositivos | Matriz RNF-082; para pruebas de almacenamiento, un Android rooteado y un iPhone con jailbreak **de laboratorio**, sin cuentas personales. |
| Secretos | Las pruebas no imprimen secretos en logs ni informes; la evidencia de configuración se archiva con valores enmascarados. |
| Registro de resultados | Cada ejecución completa: Resultado obtenido, Evidencia (ruta del informe, captura, *hash* del artefacto), Estado (`Pendiente` → `Aprobada` / `Fallida` / `Bloqueada`), fecha, versión probada y quien ejecutó (rol). |
| Fases | F2 = desarrollo (CI por PR) · F3 = QA en staging · F4 = pre-lanzamiento · F5 = piloto (`RNF` §0.2). |
| Criterio global | Una prueba **Fallida** de una amenaza con riesgo actual Alto, o de un control P0, bloquea el lanzamiento (NLS-01..NLS-03); también la bloquea si sigue **Pendiente** o **Bloqueada** (NLS-03 reformulado el 2026-11-18). Las pruebas de controles P1 siguen NLS-C2. |
